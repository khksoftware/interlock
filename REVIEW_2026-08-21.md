# Independent adversarial review — 2026-08-21

**A note on timing, first.** This repository was edited live, by its own author, while
this review was in progress: `README.md`, `docs/INTEGRATION.md`, and `docs/USAGE.md` were
modified on disk mid-session and then committed as `806f280` ("Write the README for
adopters, not for its own authors"), on top of the `b345869` ("Interlock 0.1.0") commit
this review started against. I did not make that edit, and it is a legitimate authorial
change, not a defect — its own commit message explains it (a prose tightening pass, plus a
deliberate removal of the "measured coverage" section, discussed under Claim 5 below). I
re-verified every finding below against `806f280` (current `HEAD` as of this writing)
before finalizing this report; none of the three material findings were affected by that
commit, since two are pure source-code behavior (untouched by a docs-only commit) and the
third's exact quoted text is still present, unchanged, in the new commit.

**3 material findings. The single most severe: the `absolute_local_path` git gate — the
one gate whose entire job is to refuse a commit that embeds an absolute local filesystem
path — is silently defeated by an ordinary line break in the staged content.** No
`--no-verify`, no config trick, no adversarial intent required. A path such as
`C:\Users\jdoe\Desktop\secret-plan.txt`, written across two lines exactly as a wrapped
log paste or a wrapped table cell would naturally produce it, passes the armed, installed
gate with exit 0 and zero output. This is not one of the bypasses the module discloses
(`--no-verify`, a repointed `core.hooksPath`, a deleted marker) — it is an undisclosed
false negative in the detection method itself, and it requires no bypass at all: an
entirely good-faith committer, pasting a wrapped stack trace, gets no signal that
anything went wrong.

This review is independent: I did not build Interlock, I was not told the "right"
answer, and I ran every claim below against the real artifact rather than accepting its
prose.

## Finding 1 (most severe) — `absolute_local_path` is defeated by a line break

**Claimed** (`README.md` gate table, `src/interlock/git/absolute_local_path.py`): refuses
a commit whose staged content embeds a Windows drive path, a UNC path, or a POSIX home
directory, "with an adopter-owned exemption registry for genuine citations" — implying
the only way past it is a deliberate exemption or a deliberate bypass.

**What I ran.** In a real, `interlock`-armed sandbox repository (`git.absolute-local-path`
installed and armed, verified via `interlock status`), staged this file:

```
the report lives at C:
Users\jdoe\Desktop\secret-plan.txt (see above)
```

and ran a real `git commit`.

**What happened.** The commit succeeded (exit 0), no gate output at all. The identical
path, written on one line, is correctly refused (verified separately: `C:\Users\jdoe\...`
on a single line produces `REFUSED ... embeds an absolute local filesystem path`).

**Why.** `staged_absolute_local_path_failures` (`src/interlock/git/absolute_local_path.py`,
`~line 125`) scans `content.splitlines()` and matches
`ABSOLUTE_LOCAL_PATH_PATTERNS` **per line**. All three patterns require the drive-letter
(or UNC prefix, or `/home//Users/`) and the rest of the path to co-occur in the same
line. Break the line between the colon and the separator (or anywhere else in the path)
and every pattern misses it — not because the path was disguised, but because it was
wrapped.

**Why it matters.** This is a realistic, non-adversarial way to defeat the one gate whose
entire purpose is catching exactly this class of leak — a copy-pasted wrapped log, a
markdown table cell, an editor's soft-wrap turned hard-wrap on save. It is materially
worse than the gate's own documented limits ("not exhaustive... may need `extra_patterns`
for a local convention") because those are about patterns the gate was never asked to
recognize; this is a pattern it was built to recognize, defeated by formatting alone, with
no disclosure anywhere that line-wrapped content is out of scope.

**Related, lower-severity note.** `commit_message_pattern`'s trailer match
(`TRAILER_LINE_PATTERN`) is architecturally the same per-line design, so a trailer value
broken mid-word (e.g. `Co-Authored-By: Cla` / `ude <noreply@anthropic.com>` on two lines)
would also evade it. I did not commit this as a separate finding: unlike a wrapped path,
nothing produces a broken commit trailer by accident — a harness's auto-injected trailer
is always a single well-formed line, so this variant needs deliberate construction rather
than ordinary formatting. Flagged for completeness, not counted as material.

## Finding 2 — the README's own "Path 1" quickstart is not runnable as printed

**Claimed** (`README.md`, "Path 1 — git-action gates only"): four `interlock install`
commands, printed back-to-back, are presented as the first-class quickstart for the git
host alone:

```bash
interlock install git.protected-paths
interlock install git.absolute-local-path
interlock install git.synthetic-git-identity
interlock install git.commit-message-pattern
```

**What I ran.** A brand-new `git init` repository, nothing else present, `interlock`
`pip install -e`'d into a fresh venv from a fresh Python interpreter (not the repo's own
environment) — exactly the "stranger with the docs" scenario the review brief specifies.
I ran the four lines above, in the printed order, with no deviation.

**What happened.**

```
hook installed: .../hooks/pre-commit           (git.protected-paths -- succeeds)
absolute-local-path gate: a pre-commit hook that is not this shim is already
  installed at .../hooks/pre-commit; refusing to overwrite it.               (FAILS)
synthetic-git-identity gate: a pre-commit hook that is not this shim is already
  installed at .../hooks/pre-commit; refusing to overwrite it.               (FAILS)
hook installed: .../hooks/commit-msg           (git.commit-message-pattern -- succeeds)
```

Only 1 of the 3 `pre-commit`-hook gates in the quickstart end up actually wired. This is
not a corner case: the README's own gate table, two sections later in the same document,
states plainly that `protected_paths`, `absolute_local_path`, and `synthetic_git_identity`
all fire on `pre-commit`, and git dispatches exactly one file per hook name — so this
collision is guaranteed, every time, for anyone who runs Path 1 exactly as printed.

**Why it matters.** The remedy exists and is well-written — `docs/INTEGRATION.md` §5,
"What to do when a pre-commit hook already exists," three options including a
tested compose-by-hand pattern. But the README's own "Path 1" snippet, presented as "a
first-class, common case, not a subset of some larger requirement," gives no warning this
is coming, doesn't sequence the commands to dodge it (e.g. `--install`-ing only one
`pre-commit` gate and `arm`-ing the rest), and doesn't cross-reference §5. A stranger
following only `README.md` — which is exactly what the review brief specifies as the exit
condition — hits a hard failure on the third line of the very first code block meant to
demonstrate the git-only adoption path.

## Finding 3 — `interlock status` misreports "installed" for the docs' own prescribed fix

**Claimed** (`README.md`): "`interlock status` reports both facts (installed/wired, and
armed) for every gate and hook this distribution ships... Conflating 'installed' with
'therefore enforcing' is exactly the invisible gap arming exists to close; a status
command that only reported one of the two facts would reintroduce it in a different
form."

**What I ran.** Continuing directly from Finding 2's repository: I applied
`docs/INTEGRATION.md` §5's own recommended remedy — hand-wrote one composed `pre-commit`
shim (following the documented shape: check each gate's marker, `exec` each gate's CLI in
turn), then armed `git.absolute-local-path` and `git.synthetic-git-identity` with
`interlock arm` (not `install`, exactly as §5 instructs, "since it would try to write the
shim again and hit the same refusal"). I then verified, with a real `git commit`, that
all three composed gates (`protected_paths`, `absolute_local_path`,
`synthetic_git_identity`) do actually refuse real bad commits — they do, every one,
confirmed independently.

**What happened.** `interlock status` reports, for all three correctly-armed,
actively-enforcing gates:

```
git.protected-paths        [git ] a FOREIGN hook occupies this name; armed in this worktree
git.absolute-local-path    [git ] a FOREIGN hook occupies this name; armed in this worktree
git.synthetic-git-identity [git ] a FOREIGN hook occupies this name; armed in this worktree
```

**Why.** `_git_status_line` (`src/interlock/cli.py`) reads "installed" as "the file at
the shared hook path is byte-identical to `gate.spec.shim`" — the single-gate reference
shim. A hand-composed, multi-gate shim (the docs' own prescribed fix for Finding 2) is
never byte-identical to any one gate's reference shim, so `status` calls it "FOREIGN" —
indistinguishable, in its own words, from a hook this package has no relationship to at
all — even though the gate is demonstrably wired, armed, and refusing real commits.

**Why it matters.** This is the exact failure `status`'s own stated purpose says it
exists to prevent, just inverted: instead of hiding "installed but not actually
enforcing," it now falsely claims "not managed by this package" about a gate that is
being enforced correctly. An operator who trusts `status`'s literal words has every
reason to conclude their gates are unprotected when they are not — and a maintainer who
"fixes" the alarming FOREIGN line by discarding the hand-composed shim would silently
break protection that was, in fact, working.

## Everything else I checked

### Claim 1 — docs walkthrough (README, INTEGRATION, USAGE only)

`PYTHONPATH`, to exercise the "properly install" path too). Findings 2 and 3 above came
directly out of this walkthrough. Every other documented step — configuring

both hosts, the stash gate's separate, deliberate install — worked exactly as written,

### Claim 2 — three independently-adoptable paths
`git grep`'d both subpackages directly: zero references to `interlock.turn` inside
`interlock/git/`, zero references to `interlock.git` inside `interlock/turn/`, beyond
docstring prose. `interlock.config`, `interlock.arming`, `interlock.plumbing` are genuinely
host-neutral (no import of either host). Ran `tests/test_module_independence.py`
(part of the full 231-test run, all green) — it does what its docstring claims: a
physical, on-disk deletion of one host's directory, followed by a real subprocess
`git commit` refusal (turn absent) and a real armed/unarmed turn-hook subprocess
invocation (git absent).

One non-material methodology note: `test_a_real_install_and_a_real_commit_refusal_work_with_turn_absent`
asserts only `commit.returncode != 0`, which would still pass if a future regression made
the gate *crash* (ImportError, exit code non-zero for a different reason) rather than
*refuse* — it doesn't distinguish "refused" from "broken." Today this is moot (no such
import exists, confirmed by grep), and the sibling `test_every_git_gate_module_imports_with_turn_absent`
would independently catch that regression — but the end-to-end test's own assertion is
weaker than its docstring's claim of "the end-to-end proof."

### Claim 3 — arming discipline

disarming/re-arming is disclosed every time, never silent. The one place `status` is
actually wrong is Finding 3 above, which is a real defect, not merely a documented
trade-off.
